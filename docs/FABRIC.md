# Microsoft Fabric: the match feed, live and at league scale

Two things, both on a Fabric trial capacity, so nothing to pay:

1. **Live.** The same Event Hubs feed the gateway reads also lands in a Fabric **Eventhouse** through an **Eventstream**. A **Real-Time Dashboard** shows the score, the xG race, tempo, passing, a shot map, a ball heat map, and how many seconds an event takes from the engine to a queryable row.
2. **League.** The 200 synthetic matches (`scripts/export_dataset.py`) go into a **Lakehouse** in OneLake as Delta tables, and a **Power BI** report reads them with Direct Lake: the league table, xG against goals, passing styles, home advantage.

Everything here is synthetic Northbridge League data (docs/03). Real footage from `vision/` never goes to Fabric.

Status: the KQL, the notebook, the upload script and the measures are written and tested offline (`backend/tests/test_fabric.py` runs the notebook's SQL on SQLite over exported matches). The Fabric items themselves have not been created yet. That is portal work, below.

## What is in `fabric/`

| File | What it does |
|---|---|
| `kql/00_reference.kql` | `Clubs()` and `Players()`: codes to invented names. Generated by `uv run python -m fabric.build_reference` |
| `kql/01_tables.kql` | `PitchsideRaw` landing table and its JSON mapping; update policies that split it into `MatchEvents` and `BallFrames` |
| `kql/02_functions.kql` | One function per dashboard tile: `Score`, `XgRace`, `Tempo`, `Passing`, `Shots`, `BallHeat`, `HardPassers`, `Freshness`, `LiveMatches` |
| `kql/03_dashboard.kql` | The tile queries and which visual each one uses |
| `notebooks/load_northbridge.py` | Lakehouse notebook: Parquet and clubs.json into Delta tables, plus `team_match` and `league_table` |
| `upload_to_onelake.py` | Puts the export into the lakehouse, keyless, over OneLake's ADLS Gen2 API |
| `powerbi/measures.dax` | Report measures and the relationships to set |

## Before you start: the account

Fabric needs a work or school account in the **same Microsoft Entra tenant as the Azure subscription**, because the workspace identity has to be given a role on our Event Hubs namespace, and that only works inside one tenant. A personal Microsoft account cannot start a Fabric trial.

If VJ's Azure was set up with a personal account, VJ creates one user for this (2 minutes):

1. Portal, **Microsoft Entra ID** > **Users** > **New user** > **Create new user**. User principal name `fabric`, domain the `...onmicrosoft.com` one, display name `Pitchside Fabric`. Copy the password. Create.
2. Resource group `pitchside` > **Access control (IAM)** > **Add role assignment** > **Reader** for that user (so it can see the Event Hubs namespace in pickers).
3. Sign in to [app.fabric.microsoft.com](https://app.fabric.microsoft.com) as that user (private window), set the new password.

## Steps

### 1. Trial capacity and workspace (5 minutes)

1. In [app.fabric.microsoft.com](https://app.fabric.microsoft.com), select your profile picture (top right) > **Start trial** (or **Free trial**). Pick a region close to Sweden Central. This gives 60 days of trial capacity.
2. **Workspaces** > **New workspace**, name `pitchside`. Under **Advanced**, license mode **Trial**. Apply.
3. In the workspace: **Workspace settings** > **Workspace identity** > **+ Workspace identity**. Copy its **ID**. This is how Fabric signs in to Event Hubs without a key.

### 2. Let Fabric read Event Hubs, keyless (Person A, 2 minutes)

Our namespace has local auth (keys) switched off, so the Eventstream connects as the workspace identity.

1. Portal, the Event Hubs namespace in `pitchside` (`evhns-...`) > **Access control (IAM)** > **Add role assignment**.
2. Role **Azure Event Hubs Data Receiver** > **Next** > **User, group, or service principal** > **Select members**, paste the workspace identity ID (or search `pitchside`) > **Review + assign**.

The Basic tier has only the `$Default` consumer group. The gateway reads it too; Event Hubs allows several readers on one group, so both see every message.

### 3. Lakehouse and the 200 matches (10 minutes)

1. In the workspace: **New item** > **Lakehouse**, name `pitchside`.
2. On your machine, with `az login` as the Fabric user:
   ```bash
   uv run python -m scripts.export_dataset                         # 200 matches, about a minute
   uv run python -m fabric.upload_to_onelake --workspace pitchside --lakehouse pitchside
   ```
   It prints four files under `Files/northbridge/`. (Or upload them by hand: lakehouse > **Files** > **...** > **Upload**, into a folder `northbridge`.)
3. Workspace > **Import** > **Notebook** > **From this computer**, pick `fabric/notebooks/load_northbridge.py`. Open it, **Add data items** > the `pitchside` lakehouse, then **Run all**. The last cell shows the league table. Six tables appear under **Tables**: `clubs`, `players`, `matches`, `events` (545,639 rows), `team_match`, `league_table`.

### 4. Power BI report (15 minutes)

1. In the lakehouse: **New semantic model**, name `Northbridge League`, tick all six tables, **Confirm**.
2. In the model: drag the five relationships listed at the top of `fabric/powerbi/measures.dax`.
3. Add each measure from that file (select `team_match` > **New measure**, paste one, Enter).
4. **New report**. A suggested first page:
   - Table: `clubs[club]`, `Position`, `Played`, `Points`, `Goal difference`, `xG for`, `Goals minus xG`, sorted by `Position`.
   - Scatter: X `xG for`, Y `Goals for`, details `clubs[club]`: who finishes above their chances.
   - Clustered bar: `Pass completion %` and `Ball wins per game` by club: possession sides against pressing sides.
   - Card: `Home win %`.
5. Save as `Northbridge League`.

### 5. Eventhouse and the live feed (15 minutes)

1. Workspace > **New item** > **Eventhouse**, name `pitchside`. It creates a KQL database `pitchside`.
2. Open the database > **Query with code**. Paste and run, one block at a time (select a block, Shift+Enter): `fabric/kql/00_reference.kql`, then `01_tables.kql`, then `02_functions.kql`.
3. Workspace > **New item** > **Eventstream**, name `pitchside-feed`.
4. **Connect data sources** > **Azure Event Hubs** > **Connect**. Feature level **Extended features**. Namespace `evhns-...`, event hub `match-events`. **New connection**, authentication kind **Workspace identity**, data gateway **none**. Consumer group `$Default`, data format **JSON**. Next, **Fixed schema** (or skip schema), **Connect**, **Add**.
5. On the canvas: **Add destination** > **Eventhouse**. Ingestion mode **Direct ingestion**, workspace `pitchside`, Eventhouse `pitchside`, database `pitchside`, table **existing** `PitchsideRaw`, data format **JSON**, mapping **PitchsideRawMapping**. Save, then **Publish**.
6. Make some traffic. With `EVENT_BUS=eventhubs` and the Event Hubs settings in `.env`:
   ```bash
   make dev
   curl -X POST "http://localhost:8000/matches/derby_01/live/start?speed=10"
   ```
   Or call the same endpoint on the deployed api. In the KQL database, `MatchEvents | take 10` should return rows within a minute.

### 6. Real-Time Dashboard (10 minutes)

1. Workspace > **New item** > **Real-Time Dashboard**, name `Pitchside live`. Data source: the `pitchside` KQL database.
2. **Manage** > **Parameters** > **New**: label `Match`, variable `_match`, type string, single selection, source **Query** `LiveMatches() | project match_id`, default **first value**.
3. Add one tile per block in `fabric/kql/03_dashboard.kql`, with the visual named in its comment.
4. **Manage** > **Auto refresh** on, minimum 10 seconds. Save.

Start a live match (step 5.6) and the tiles follow it. The **Event Hubs to Eventhouse latency** tile is the number for the README: engine publish to queryable row, p50 and p95.

## Cost

The trial capacity is free for 60 days, which covers the hackathon and judging. Event Hubs is already paid for. When the trial ends the items stop, and nothing bills unless someone buys a capacity. Do not buy one.

## Checking it worked

- `MatchEvents | summarize count() by match_id` counts about 2,700 events for a full match.
- `Score('derby_01')` matches the score on the broadcast.
- `league_table` in the lakehouse has 8 rows; played adds up to 400 (200 matches, two sides each).
